# BE08C2: удаление регистрации с сохранением работы

Основание: согласованные пользователем административные исключения после сдачи и обязательная сохранность существующих Project-программ. C00 1.20.0 добавляет отдельные команды решений. Старые обработчики удаления участников/регистраций не изменяются.

Организатор/admin своей программы отправляет `registration_ids` — ID PartnerProgramUserProfile, а не User или решения — в `POST /programs/{program_id}/management/registrations/remove/preview/`. Выборка содержит 1–10000 уникальных безопасных целых ID; чужие или отсутствующие регистрации дают 404. Preview показывает выбранных людей и эффекты по каждой активной работе. Применение по `/apply/` требует точный подписанный token, привязанный к организатору, программе, выборке, текущим регистрациям/людям/работам/файлам/составу/приглашениям/оценкам/назначениям. Срок подтверждения 10 минут. Изменение состояния, повтор, подмена или истечение подтверждения дают 409; права проверяются заново. Неизвестные body/query запрещены. Ответы private, no-store.

В одной транзакции с блокировками program → выбранные profiles → решения по ID выполняются следующие эффекты:

- Капитан выбранной активной заявки: архив reason=`registration_removed` через общий writer BE08C1. Материалы, UserFile, исходная сдача, состав и оценки сохраняются. Pending-приглашения и все назначения снимаются; оцененные назначения также снимаются, оценки остаются. Черновик получает archive_snapshot без искусственной сдачи.
- Принятый участник: удаляется из текущего состава и текущего сданного снимка; исходный состав и новая ревизия записываются в историю. Материалы, оценки, назначения и обработанные приглашения сохраняются. Связанные pending отзываются.
- Получатель только pending-приглашения: pending отзывается, состав и снимок материалов не меняются; появляется ревизия и история. Историческое принятое приглашение само по себе не дает доступ к материалам.
- Регистрация без активной работы: удаляется с самостоятельной записью аудита. Архивные работы, их состав, снимки и прежняя история не меняются.

Несколько выбранных участников одной работы дают одну ревизию. Если выбран ее капитан, применяется один архивный эффект с сохранением состава. Затем удаляются только выбранные регистрации этой программы. Auth User, роли manager/expert, экспертные оценки и другие программы не удаляются. Закрытый прием/выключенный creation flag не блокируют административное исключение. Новая заявка капитана возможна только после регистрации и при соблюдении обычных условий программы.

Если профиль содержит Project или выбранный человек связан с Project-заявкой этой программы как руководитель, участник или получатель приглашения, вся команда получает `legacy_application_conflict` без изменений. Она не пытается автоматически исправлять смешанные данные. В legacy_project режиме новый адрес возвращает `solution_mode_unavailable`; действующие маршруты продолжают работать.

Неизменяемый SolutionRegistrationRemoval хранит программу, организатора, время и минимальные пары registration_id/User без копии анкеты и email. Он существует независимо от решения. Список `/management/registrations/removals/` поддерживает offset/limit; detail `/{audit_id}/` возвращает аудит и связанные изменения. Доступ только у организатора/admin своей программы. SolutionAdministrativeChange получает ветку `remove_registrations` с removed_members и registration_removal_id; архивный эффект содержит optional registration_removal_id. Старые case/member/archive payloads сохраняются.

Миграция 0038 добавляет аудит и nullable-связи истории, без удаления/архивации/переноса существующих записей. Она применяется до backend, затем frontend. После первого C2 события readers/backend/workers сохраняют поддержку C00 1.20; поля и аудит не откатываются вниз. Creation-only rollback продолжает выключать только создание. Для полного REL01 все еще нужна приемка первого выпуска.

Реализован frontend port/adapter/repository и четыре use cases с общим C00. Новый organizer UI/подтверждение/журнал и навигация архива следуют согласованию D02; D03 и конкурсная eligibility несданных черновиков остаются открыты. Этот backend/API checkpoint не заменяет эти экраны или исходный QA01. Реальные программы не переключались; merge/deploy/BE10 не выполнялись.
