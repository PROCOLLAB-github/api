## Порядок разработки

C00 фиксирует техническую основу. D00 v3 явно согласован пользователем 24 октября 2026 года в чате. BE01 и FE01 реализуются параллельно по C00. Для следующих задач сохраняется согласованный дизайн и порядок зависимостей ТЗ.

## Решения C00

Одна основная сущность ProgramSolution одновременно представляет заявку команды и ее решение. Команда состоит из принадлежащих заявке записей участников. Самостоятельная Team, обязательный Project, отдельная Application поверх решения и процесс повторной сдачи не вводятся.

Решение принадлежит одной программе. Формат формы — case_championship или hackathon. У программы одна общая форма; разные поля по кейсам не входят в v1. Кейс или задача представлены полем select с purpose:case, без новой сущности Case. Поля шаблона копируются в конфигурацию программы.

Создание доступно по текущим правилам участника и дедлайна, включая существующие административные исключения. Повторное создание капитаном возвращает его заявку с HTTP 200; новое — 201. До первого включения все изменяющие endpoints проверяют технический режим программы. Наличие серверного кода при выключенном режиме не дает создать решение.

## Метаданные существующей страницы программы

GET /programs/{id}/ дополнительно передает read-only `solution_storage_mode: legacy_project | solution` в member и unregistered вариантах. Это только выбор маршрута; поле не открывает описание, форму, состав, ответы или оценки. `current_application` сохраняет прежний Project DTO. Верхний экспертный вход и ссылка виджета ведут в `solutions-rating` только при явном `solution`, иначе в `projects-rating`. Старый клиент игнорирует добавочное поле; новый клиент при его отсутствии сохраняет старый путь. Rollout: backend → frontend, без миграций. Эта совместимая метаинформация существующего API не добавляет операции к 34 операциям решения и не меняет JSON-схемы C00 1.6.0.

Капитан также имеет одну запись ProgramSolutionMember. При создании она добавляется в той же транзакции. При передаче капитанства меняется captain FK на уже принятого участника; прежний капитан остается участником. is_captain вычисляется сравнением user.id и captain_id. Дублировать капитана в численности нельзя.

Ограничения БД: unique(solution,user) для участников; unique(solution,field) для ответов; частичный unique(solution,recipient) для pending приглашений; положительные версии; submitted_at и snapshot заполнены только в submitted. FK ссылаются на реальное решение без фиктивного Project.

Инвариант «капитан входит в состав» и соответствие поля программе проверяются сервисом в транзакции. Их нельзя выразить обычным CHECK по строке. Создание дублей и запрет участия в двух командах активной программы обеспечиваются сериализацией через программу и повторными проверками всех поддерживаемых способов записи. Не объявляем динамическую exclusivity ограничением unique(user,program) навсегда.

Физически новые приглашения хранятся в SolutionInvitation, а старые Invite не получают фиктивный project FK. Общая бизнес policy используется через адаптер владельца. Операции отзыва сохраняют действующую семантику удаления: pending приглашение удаляется; статус revoked не добавляется. accepted и declined остаются историческими строками.

BE04 добавляет nullable JSON-колонку PartnerProgramField.solution_options для точного хранения вариантов, включая символ |. При null чтение использует прежний options; старые определения автоматически не переписываются. Новая форма сохраняется целиком через solution-form. Прежний project-form не изменяет определения нового конструктора, в том числе после технического выключения режима.

## Ревизии

ProgramSolution.version начинается с 1 и увеличивается при каждом успешном изменении содержимого, состава или приглашений и при сдаче. Изменение разрешений из-за времени или роли и изменение формы организатором само по себе версию решения не повышают.

SolutionInvitation.version начинается с 1 и повышается при редактировании и принятии либо отклонении. Отзыв удаляет строку. Ревизия приглашения не заменяет актуальные проверки состава.

Form.revision — непрозрачный 64-символьный SHA-256 в hex от канонической конфигурации: template и определения в порядке position с ID, типом, назначением, подписью, подсказкой, обязательностью, options и validation. Используется существующий механизм хеша; одинаковая конфигурация дает одинаковую ревизию. Клиент сравнивает строки и не вычисляет хеш. Сам hash не является номером версии документа 1.0.0.

- PATCH решения и submit требуют expected_version и expected_form_revision.
- Команды состава требуют expected_solution_version.
- Создание приглашения требует expected_solution_version.
- Редактирование приглашения требует expected_version приглашения и expected_solution_version.
- Accept и decline требуют только expected_version приглашения: получатель до вступления не должен читать закрытую заявку.
- DELETE приглашения передает обе ожидаемые версии в query. DELETE участника — expected_solution_version в query.
- PUT формы требует expected_revision.

Состояние и права всегда повторно проверяются внутри транзакции. Ошибка ревизии — 409 version_conflict либо form_revision_conflict без записи. Клиент перечитывает объект, сохраняет локальные правки и предлагает повторить осмысленное действие. Автоматически повторять submit или принятие приглашения после конфликта нельзя.

## Общие правила API

API base URL берется из настроек окружения. Новые пути добавляются к тому же base URL, что /programs/ и /projects/. Отдельный /v1 в URL не добавляется; версия пакета контракта — 1.0.0.

JWT Bearer и текущие правила аутентификации сохраняются. ID — положительные JSON integer не больше 2^53−1. Даты — ISO 8601 UTC с Z. Пагинация: limit от 1 до 100, default 20; offset от 0. Ответ: count, next, previous, results.

Тело запроса строгое: неизвестные поля отклоняются; поля пользователя, роли авторизации, project_id, team_id и submitted не принимаются в командах, где они не определены. Клиенты должны терпимо читать дополнительные поля ответов при совместимом расширении контракта.

Все несекретные публичные подписи имен полей берутся из определения формы. Поля ответа запроса могут возвращать только данные разрешенной заявки. Смена ID в URL не переносит объект в другую программу.

## Чтение и полномочия

Капитан и принятые участники читают заявку. Организатор, эксперт и прочие зрители получают доступ в пределах текущей политики программы, назначений и публикации работ. Это не дает прав изменения или сдачи за капитана.

permissions в Solution вычисляются для текущего пользователя: can_edit, can_manage_team, can_invite, can_submit и can_leave. У участника и эксперта нет прав редактирования, управления командой, приглашения и сдачи. Принятый участник может получить can_leave для собственного выхода. can_submit означает, что капитану разрешена команда сдачи по состоянию и срокам; неполнота полей отражается отдельно в readiness. Это позволяет нажать действие и увидеть причины неготовности.

readiness содержит is_ready и issues. Для неконкурсных заявок и зрителей вне своей команды возвращается null. Для своей команды выводятся актуальные требования без раскрытия чужих персональных данных. Разрешение на действие не вычисляется на фронте по роли или часам браузера.

Приглашение до принятия раскрывает program, безопасную ссылку solution, капитана, получателя и текст приглашения. Ответов формы, состава чужой команды, регистрационных анкет и оценок в нем нет. Входящий список содержит только приглашения текущему пользователю; список приглашений заявки доступен капитану. Административное чтение сохраняет действующий отдельный объем полномочий и не подразумевается этим endpoint.

Если объект вне видимости вызывающего, возвращается 404. Если объект видим, но действие запрещено, — 403. Для новых API 401, 403 и 404 также имеют общий Error envelope. Старые endpoints не переводятся на него автоматически.

## Команда и приглашения

### Пользовательский путь из действующего проекта

Заявка имеет две вкладки: «Решение» и «Команда». На первой — настроенные поля и материалы, на второй — строки принятого состава и отдельный список «Ожидают подтверждения». Это разделы одного ProgramSolution. Переключение сохраняет локальный ввод; общее сохранение и сдача относятся к обеим вкладкам. При ошибке сдачи открывается нужная вкладка.

Источник текущего UI исправлен после предоставленных пользователем скриншотов: локальный ref origin/master, commit 8a064835, компоненты project-member-invite-modal, participant-picker, project-invite-role-input и project-team-step. Старый checkout f6f867c6 с inline формой по ссылке не является источником целевого сценария. Ссылка на профиль не вводится.

«Пригласить участника» открывает модальное окно. В нем поиск по имени или фамилии от двух символов, нормализация пробелов, задержка 300 мс и отмена предыдущего запроса. Переиспользуется существующий GET `/auth/public-users/` с `user_type=1`, `fullname`, `partner_program=solution.program_id`, `limit=8`, `offset=0` через GetMembersUseCase и MemberHttpAdapter. program_link_id не подставляется вместо ID программы. Ответ использует действующую модель User и карточку имени, возраста, специальности и навыков; новый каталог API не вводится.

Получатель выбирается из результата. Капитан, принятый участник и уже приглашенный человек недоступны с объяснением причины. Выбор заменяет список карточкой «Выбранный участник», которую можно очистить. В createInvitation передается существующий `recipient_user_id` выбранного пользователя; текст поиска не является выбранным ID.

Роль обязательна в форме: после нормализации пробелов от 1 до 128 символов. Сохраняются 13 подсказок ProjectRoleSuggestions, их фильтрация и свободный ввод. Отправка активна только при валидных получателе и роли; pending блокирует повтор. Ошибка оставляет выбор и роль, успех закрывает окно и добавляет ожидающее приглашение. Отмена и новое открытие сбрасывают временную форму; закрытие прекращает обновление из старого запроса.

В ожидающих приглашениях сохраняются видимые действия изменения роли и отзыва с подтверждением. Прежнее описание об отсутствии видимой кнопки редактирования относилось к старому checkout и исправлено. После сдачи применяются ограничения C00: редактирование роли и принятие запрещены, отзыв и отклонение доступны. Получатель использует существующие входящие приглашения и принять/отклонить, ссылка адаптируется к Solution.

Схемы C00 для создания по recipient_user_id, изменения и отзыва уже поддерживают этот путь и не менялись. Nullable role на уровне API сохранен для совместимости с legacy моделью; UI требует заполненную нормализованную роль. Существующие проектные endpoints сохраняют работу; решения используют свой контракт. Ошибки показываются безопасным сообщением без raw backend body. Черновик заявки не отправляет приглашение автоматически.

Принятый состав представлен team.members. accepted_count равен количеству уникальных членов, включая капитана. pending_count — уникальные pending получатели. reserved_count — количество уникальных пользователей в объединении принятого состава и pending получателей; при штатных данных равно сумме двух счетчиков.

При создании и принятии приглашения проверяются регистрация, отсутствие в принятом составе, запрет второй команды активной конкурсной программы и максимум с резервами. При принятии свой резерв заменяется принятым участием и не увеличивает число занятых мест второй раз.

На submit минимум и максимум проверяются по принятому составу, как сейчас. Не принявшие приглашение пользователи не закрывают минимум. Новая заявка допустима с одним капитаном. NULL отключает соответствующую границу. Источник границ — текущие параметры legacy_team_min_size и legacy_team_max_size через адаптер, без импорта параметров из независимого nextgen процесса.

Exclusivity действует в конкурсной программе до datetime_finished. В другой программе и после завершения программы ложного конфликта быть не должно. При сосуществовании старых заявок и новых решений проверяются обе структуры; pending приглашения сами по себе не считаются принятым участием во второй команде.

После submit состав и приглашения нельзя создавать, менять или принимать. Pending приглашения разрешено отклонить или отозвать, что изменяет служебную version и счетчики, но не снимок сданного принятого состава. Зафиксированная работа не размораживается.

remove и transfer возвращают MutationReceipt с новой solution_version; клиент перечитывает доступное решение. Leave возвращает 204, поскольку вышедший пользователь может утратить право чтения. Accept возвращает обновленное приглашение, ссылку заявки и новую solution_version; decline возвращает application:null и solution_version:null. Удаление капитана и его выход запрещены до передачи капитанства. Прямого POST members для обхода приглашения нет.

## Ответы и формы

Ответ представлен как {field_id,value}. Тип берется из определения поля, а не из переданного клиентом type:

| Тип                 | JSON value                        |
| ------------------- | --------------------------------- |
| text, textarea, url | string                            |
| select, radio       | Точная строка из options          |
| number              | JSON number, включая 0            |
| checkbox            | boolean, включая false            |
| file                | {url: URL существующего UserFile} |

PATCH с value:null очищает ответ. Пустая строка и строка из пробелов также очищают текст, ссылку и выбор в черновике. В ответе GET очищенные поля отсутствуют в answers, не содержат null. Дубликат field_id в запросе отклоняется целиком. Сохраненный текст не меняется автоматически, кроме нормализации, предусмотренной текущим полем; проверка пустоты использует trim.

Проверка типов, вариантов и ограничений выполняется при каждом непустом сохранении. Required применяется при submit. Число 0 и false удовлетворяют обязательности ответа; отдельное согласие с требованием true в v1 не добавляется. Системное название ограничено 256 символами, создается по текущему правилу начального названия и обязательно при сдаче.

Типы: text, textarea, url, number, select, checkbox, file. radio сохраняется для существующих определений и переноса; новый конструктор не предлагает его создание. purpose:case допустим только для select и в единственном экземпляре; сервер сохраняет системное name=case. Подпись «Задача или трек» в хакатоне не меняет эту семантику. Системные назначения, кроме other, уникальны в форме. presentation требует file; repository, demo и video требуют url; run_instructions требует textarea. Любой поддерживаемый тип можно использовать с purpose:other.

position — уникальные целые числа от 0; PUT нормализует порядок в последовательность. options хранятся точными строками, пустые и дубли после trim без учета регистра запрещены. Используемые значения нельзя переименовать или удалить. Select в сохраняемой конфигурации требует хотя бы один вариант; шаблон возвращает пустые options как заготовку для организатора.

До первого PUT конфигурация может иметь template:null, fields:[], is_configured:false. Это блокирует создание новых решений с кодом form_not_configured. GET формы при этом допустим организатору и зарегистрированному участнику, а не генерирует автоматически выбранный шаблон.

## Настройка организатором

PUT management/solution-form полностью заменяет определения с expected_revision. id:null означает новое поле, пропуск существующего ID — удаление. Чужой ID и повтор одного ID отклоняются. Системное name не редактируется клиентом.

После непустых ответов нельзя удалить поле или сменить его тип. Использованные варианты нельзя удалить или переименовать. Допустимо добавить поля, менять подпись, подсказку, порядок и required. Ограничения сужаются только если им соответствуют все сохраненные непустые ответы. Смена template после has_answers:true запрещена. Новая required настройка влияет только на несданные работы.

В FormManagement fields_usage содержит возможность удаления и смены типа, а affected_draft_count — количество черновиков, которые после применения конфигурации не готовы по новым обязательным полям. При GET это количество по текущей конфигурации; после PUT — по сохраненной. Фронт не вычисляет счетчик по загруженной странице заявок.

Начальные шаблоны копируются в конкретную программу. В КЧ требуются выбор, краткое описание и PDF, в хакатоне — выбор, краткое описание, описание реализации, репозиторий и инструкция запуска. Демо, видео и дополнительные материалы необязательны; в хакатоне также необязательна презентация. Иные поля добавляет организатор. Это стартовые требования, не отдельные классы решения.

## Файлы

POST /files/ принимает multipart file и возвращает ровно существующий {url}. На привязке file поля сервер ищет UserFile по link и проверяет право использования: собственная загрузка капитана либо файл, уже принадлежащий этой заявке, в том числе из переноса. Произвольная внешняя ссылка не становится file ответом. Внешние материалы добавляются через поле url.

Один file ответ содержит один файл. Верхний предел привязки к решению в v1 — 100 MiB (104857600 bytes); поле может задать меньший предел. Существующий общий upload сохраняет свои ограничения для остальных потребителей. Фронт проверяет размер по определению поля до загрузки, а backend повторяет проверку при привязке UserFile. Для PDF в шаблоне КЧ — 20 MiB и extension pdf. Для дополнительных архивов задается отдельное поле; начальный предел 50 MiB. Проверяются фактический размер и разрешенный тип, а не только строка имени. Старые заведомо импортированные материалы не блокируют чтение истории.

Снятие ответа не удаляет бинарный файл автоматически. Удаление UserFile, на который ссылается сданное решение, должно отклоняться защитой file_in_use в файловом сервисе. Действующие успешные upload ответы остаются прежними. Доступ к бинарным данным CDN остается в существующей модели; контракт не обещает новую выдачу подписанных ссылок.

## Сдача

Состояния хранения: draft и submitted. Статусы оценивания и публикации остаются производными действующего процесса.

Последовательность фронта:

1. Сохранить текущие ответы PATCH с обеими ожидаемыми ревизиями.
2. Получить новую Solution.version, не использовать старую версию до PATCH.
3. Выполнить текущее подтверждение сдачи.
4. POST submit с новой expected_version и actual expected_form_revision.
5. При успехе показать полученное представление submitted; при конфликте перечитать данные без автоматической повторной сдачи.

PATCH и submit — две отдельные транзакции. Если submit отклонен, ранее успешно сохраненный черновик остается сохраненным; частично сданного состояния не возникает.

Под блокировками повторяются проверки капитана, конкурсности, состояния, дедлайна, состава, выбора, всех required и ограничений. Успех записывает status, submitted_at, version и submission_snapshot атомарно. Снимок включает название, form definitions, form revision, answers, капитана и принятый состав. Pending приглашения в состав снимка не входят.

Для draft GET возвращает текущую form и is_snapshot:false. Для submitted — form и answers из снимка с is_snapshot:true. Новый required, новая подпись или порядок не меняют сданный просмотр. Состояние таймера submission_open при этом вычисляется на момент GET и не является частью исторических требований.

После сдачи повторный submit дает 409 already_submitted независимо от старой expected_version, после проверки доступа и роли. Не вводятся повторная сдача, отзыв сдачи или возврат в draft. При сетевом обрыве клиент делает GET и устанавливает фактический статус.

Дедлайн: отдельная дата подачи либо дата окончания регистрации. Сравнение сохраняет текущую включенную границу: серверное now <= deadline. После закрытия подачи нельзя создавать и сдавать, но несданный черновик можно сохранять, как в действующем API. Конкурсность отдельно управляет submit: в неконкурсной программе status остается draft, submission.required:false, readiness:null, can_submit:false; работа сохраняется без искусственной сдачи.

## Ошибки

Новый Error содержит обязательные code, detail, errors и meta. errors — массив {path,code,field_id,detail}; field_id:null для системной ошибки. meta несет current_version или current_form_revision только при наличии права чтения.

| HTTP | Коды                                                                                                                                     |
| ---- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| 400  | validation_error, invalid_answers, required_program_fields, case_required, case_unavailable, invalid_form                                |
| 401  | authentication_required                                                                                                                  |
| 403  | not_program_member, not_solution_captain, not_invite_recipient, permission_denied                                                        |
| 404  | not_found                                                                                                                                |
| 409  | solution_mode_unavailable, form_not_configured, version_conflict, form_revision_conflict, already_in_program_team, ambiguous_application |
| 409  | team_frozen, team_min_size, team_max_size, already_solution_member, duplicate_pending_invite, invite_already_processed                   |
| 409  | captain_cannot_leave, captain_cannot_be_removed, captain_already_selected, not_solution_member                                           |
| 409  | submission_closed, already_submitted, not_competitive, field_in_use, template_locked, file_in_use                                        |

Это HTTP контракты новых endpoints. Существующие статусы старых /projects/, /invites/ и submit связи не меняются. Повторное действие с удаленным приглашением дает 404. Повтор accept/decline сохраненной обработанной строки — 409 invite_already_processed.

Приоритет проверок: аутентификация → существование и видимость → право действия → финальное состояние → ожидаемые ревизии → валидация текущих бизнес правил и значений → запись. На уже сданной работе submit дает already_submitted, edit дает team_frozen; на уже обработанном приглашении accept/decline дают invite_already_processed. Внутри блока нарушений дедлайн проверяется перед составом и полями. Синтаксическая проверка запроса может выполняться до загрузки объекта.

## Транзакции и совместимость

Для новых writers порядок блокировок: PartnerProgram → ProgramSolution → затронутые SolutionInvitation в порядке ID → определения формы и профиль/записи участников в согласованном порядке. Config writer начинает с Program и блокирует затронутые решения в порядке ID перед определениями. Все writers работают в транзакции и повторяют проверки после блокировок. Фактический порядок внутренних таблиц фиксируется совместно в BE01–BE04; инверсия между endpoint запрещена.

Legacy порядок Project → Program → program links не меняется молча. Новый writer не пытается получить блокировку старого Project, уже удерживая Program. Проверка старого состава выполняется чтением под общей сериализацией Program. Переход программы на единственный источник записи осуществляется отдельно в BE10 с остановкой старых writers и явной таблицей соответствий.

После commit отправляются существующие уведомления и события; повторный submit или ошибка не создает их снова. Начисление оценок и выдача результата не входят в submit транзакцию.

Не подменять старые поля partner_program/project/program_link_id новыми числовыми ID. Старый и новый ID могут совпасть по значению, поэтому тип ссылки всегда задан контекстом или kind. current_application для новой навигации берется из solution-context; старые endpoints остаются в legacy adapter.

## Параллельная разработка

Backend реализует операции по operationId из openapi.json. Frontend использует те же схемы и examples.json; сценарии независимы, не описывают изменяемую in-memory базу. Сначала можно собрать FE01 и экранные моки FE02–FE06, пока идут BE01–BE06.

Фикстуры содержат успешные и ошибочные состояния, включая неполный и готовый черновик, поданную работу, неконкурсный режим, закрытый дедлайн, приглашения, конфликты ревизий, 0 и false. Даты и ID фиктивные; моки с таймером используют собственные контролируемые часы, а не текущую дату компьютера.

Изменение имен полей, required, статусов или формы ответа требует синхронного обновления этого описания, OpenAPI и примеров. Добавление совместимых endpoints или полей — minor версия; ломающее изменение согласуется до интеграции. Номер ревизии формы не используется как версия API.

## Проверка пакета

Для проверки нужны dev-зависимости jsonschema и openapi-spec-validator (`poetry install`). Они не нужны для обработки запросов продукта.

```text
python validate_contract.py
```

Скрипт проверяет корректность OpenAPI, все локальные refs и схемы, примеры request/response, уникальность operationId, базовые инварианты состава и snapshot. Реальные ответы BE01 дополнительно проверяются JSON Schema в `partner_programs.tests.test_solution_foundation`.
