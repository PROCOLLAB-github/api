# Контракт состояния «Моих проектов»

## Причина и изменение

Карточка получала наличие программы без признака сдачи, хотя detail уже возвращал
`is_submitted`. Это позволяло показывать лидеру «можно редактировать» для сданного проекта.

В ответах `GET /auth/users/projects/` и `GET /auth/users/projects/leader/`
поле `partner_program` расширено без удаления старых ключей.

До изменения:

```json
{"id": 12, "name": "Программа"}
```

После изменения для связи `PartnerProgramProject.pk=120`:

```json
{
  "id": 12,
  "name": "Программа",
  "program_link_id": 120,
  "program_id": 12,
  "is_submitted": true
}
```

`id` сохраняет смысл ID программы; `program_link_id` — ID связи проекта с программой.
`is_submitted` берётся непосредственно из `PartnerProgramProject.submitted`.
Без связи возвращается `null`. `can_submit`, `program_fields`, `program_field_values`
в сокращённый контракт не включены.

## Выбор связи и запросы

Список, как существующий detail, выбирает связь с минимальным PK. Порядок создания
программ, создания связей или переданного prefetch-кеша не влияет на выбор.
Это поддержка существующего singular-контракта, а не новый выбор программы.

Оба списка используют `Prefetch("program_links", queryset=...select_related("partner_program").order_by("pk"))`.
Сериализатор использует даже пустой кеш связей без повторного SELECT. Без prefetch
загружает одну связь и программу одним запросом с `ORDER BY pk`.

Query-count regression сравнивает 1 и 31 проект (часть без программ) для обоих API.
Результат: 3 → 3 запроса для каждого endpoint (COUNT, страница проектов, связи с
программами через JOIN). Сериализация подготовленного кеша связей — 0 запросов,
включая пустой кеш; без prefetch — 1 запрос.
Прогревается только существующий кеш `views_count`: его отдельные cache miss
в `core.services.get_views_count` не относятся к загрузке программ и не изменены.
Таким образом, замер не является заявлением об отсутствии N+1 при холодном кеше просмотров.

## Границы и проверка

Фильтры доступа лидера/участника, detail, `current_application`, сдача, case,
аналитика и React-домен не изменены. Миграций и новых зависимостей нет.

Регрессии: `users.tests.test_project_list_program_contract` — null/false/true,
обратные PK/порядок создания/порядок кеша, совпадение list/detail, одинаковая metadata
для лидера и collaborator, отсутствие доступа анонимного пользователя и query count.
Существующие проверки detail/access, submission и current_application запускаются отдельно.

Для будущего DEV-развёртывания сначала нужен этот additive backend-контракт,
затем Angular-защита неполного ответа. Merge/deploy этой задачей не выполняются.
После отдельного разрешения на deploy нужно сравнить `program_link_id` и
`is_submitted` из list/detail одного реально сданного DEV-проекта и проверить
«Сдан в программу / Лидер / только просмотр» на карточке. Сейчас live-проверка отложена.
