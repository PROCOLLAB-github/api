## Контракт

Существующие `/programs/:id/`, `/projects/`, `/manager-overview/`, экспорт и legacy scoring остаются совместимыми. Новая панель использует отдельную приватную проекцию: публичный пользовательский DTO не содержит почту участников.

Все новые URL начинаются с `/programs/:id/management/`.

| URL | Метод | Результат |
| --- | --- | --- |
| пустой путь | GET | Основное, даты, режим программы, `updated_at`, материалы |
| `participants/` | GET | DRF `count/next/previous/results`, ФИО, почта, город, регистрация именно в программе |
| `projects/` | GET | Связи Project × Program, руководитель, сдача, оценивание, кейс и презентация |
| `projects/:link_id/team/` | GET | Руководитель и действующие Collaborator: id, имя, роль, почта и nullable avatar; без приглашений и изменений команды |
| `projects/:link_id/evaluation/` | GET | Оценки критериев этой программы, реальные назначения и `can_rate` |
| `settings/basic/` | PATCH | Только поля содержания и изображений из макета |
| `settings/dates/` | PATCH | Только пять календарных полей из макета |
| `materials/` | POST | Материал с названием и одним источником: URL или UserFile |
| `materials/:id/` | PATCH, DELETE | Обновление или отвязка материала от программы |

Чтение и запись доступны только manager **этой** программы либо staff/superuser по существующему `can_manage_program`. Expert без роли manager не получает панель. Чужая программа даёт 403, отсутствующая — 404; чужая связь или материал внутри доступной программы — 404. Mutations участников/проектов отсутствуют.

Списки принимают `search`, `limit` (1–100, по умолчанию 20), `offset` (от 0). Поиск участников — AND по фрагментам, OR между ФИО и почтой; удаленные пользователи не считаются действующими участниками. По умолчанию порядок — дата регистрации/связи и PK. Проекты дополнительно принимают `submission=all|submitted|not_submitted`, `case_scope=all|selected|without_case`, при selected — точный `case_name`. Неправильные параметры возвращают 400, выдача ограничена страницей.

Участники поддерживают `activity=all|period|active|inactive`: active означает наличие `last_activity`, inactive — отсутствие даты, независимо от давности. Прежнее `never` остается alias inactive. Для period нужен хотя бы один из `activity_from` / `activity_to`, границы включают полные московские дни. `order=registration|activity_asc|activity_desc` задает порядок до пагинации; по умолчанию activity_desc (недавняя активность сверху, пустые даты в конце), для activity_asc пустые даты идут первыми, затем старые даты; одинаковые стабилизируются PK. Регион, поиск и активность сочетаются. GET `participants/export/` и `participants/selection/` применяют те же фильтры и порядок ко всем совпадениям, игнорируя пагинацию. Права организатора и формат ответа не меняются; миграций нет.

Оценивание повторно использует `_solution_rows`: в distributed учитываются завершённые реальные назначения; частичная оценка сохраняется отдельно. В open сохраняется существующая семантика наличия оценки по критериям программы. Несданное решение имеет приоритет, неконкурсное — `not_applicable`. Статусы вычисляет сервер. Презентация берётся из `Project.presentation_address` независимо от сдачи.

## Сохранение и ошибки

PATCH настроек передаёт только изменённые поля выбранного раздела и обязательный `expected_updated_at`. Program блокируется `select_for_update`; несовпадение версии —409 `stale_settings`. Переход истёкшего дедлайна в будущее или снятие необязательного дедлайна требует `confirm_reopen=true`, иначе409 `reopen_confirmation_required`, без сохранения. Пустой отдельный срок сдачи по-прежнему использует окончание регистрации. Новая хронология или новые правила сдачи не вводятся.

PATCH материала передаёт название, один источник и `expected_updated_at`; DELETE принимает ту же версию в query. Конфликт —409 `stale_material`. Для нового файла проверяется владелец; сохранённый источник допустим при редактировании другим manager той же программы. Удаление материала и замена источника сохраняют исходный UserFile/CDN-файл. Схема БД не меняется.

400 означает ошибку значений или неподдерживаемое поле. Поля managers, draft, конкурсность, права, критерии, кейсы и распределение экспертов через настройки не изменяются.

## Angular и внедрение

### Организаторы программы · DEV

`GET/POST /programs/{id}/management/organizers/` возвращает приватный состав либо
приглашает по email. `POST organizers/{user_id}/remove/` снимает доступ;
`POST organizer-invitations/{id}/resend/` и `revoke/` управляют приглашением.
Все записи требуют актуального `revision` и организатора конкретной программы
либо существующего административного scope. Изменения сериализуются блокировкой
строки программы. Последнего активного организатора снять нельзя; непринятые
приглашения и отключённые аккаунты не заменяют действующего организатора.

Публичный контекст ссылки — `/programs/organizer-invitations/{token}/`, действия —
`accept/` и `register/`. GET не выдаёт доступ. Принятие требует активного аккаунта
с почтой приглашения; регистрация нового организатора сохраняет обязательную дату
рождения. Доступ ограничен `PartnerProgram.managers`: глобальные административные
права и членство эксперта не выдаются. Снятие доступа отзывает принятые и ожидающие
приглашения этого пользователя, чтобы старая ссылка не восстановила права.

Нужна только новая таблица `partner_programs.0023_organizerinvitation_and_more`;
существующие организаторы и оценки не преобразуются. Сначала backend/migration,
затем Angular. Страницы `/organizer-invitation/` и `/organizer-password-reset/`
обслуживаются SPA; API использует уже настроенный префикс `/programs/`.
Письмо использует существующие Celery и почтовый backend, разрешённый frontend
origin из `EXPERT_WORKSPACE_FRONTEND_URL`. В БД хранится digest, повторная отправка
меняет токен, срок — 7 дней. `queued/sent/failed` описывает отправку; `sent` не
подтверждает доставку во входящие. Ответы приватные/no-store, токены скрыты в
application logger и Celery argsrepr. Сброс пароля сохраняет контекст приглашения.

Angular получает camelCase через существующий interceptor, передаёт версии, обрабатывает409, сохраняет введённые значения при ошибке и запрашивает подтверждение ухода. После сохранения сбрасывает приватный/публичный кеш программы. Даты редактируются явно в Москве UTC+3; неизменённые поля не округляются.

Переход к оценке открывает чтение выбранного проекта. Для пользователя с существующими правами эксперта дополнительная ссылка ведёт в legacy rating с точным `project_id`; фильтр не расширяет queryset доступных эксперту проектов. POST оценок и права эксперта не меняются.

Порядок внедрения: backend API → Angular UI. Только dev; merge и deployment выполняет пользователь. Отдельные действия участников, массовые операции, возврат проекта на доработку, исключение и смена кейса в V1 не входят.


## Уточнения интерфейса проектов · 21.10.2026

GET `management/projects/export/` использует тот же ManagementProjectQuery, что список (поиск, кейс, сдача, оценивание), до пагинации. Приватный XLSX содержит все совпадения, включая другие страницы; текстовые данные сохраняются строками без исполнения Excel-формул. Права те же, что для списка.

`management/projects/:link_id/evaluation/` дополнительно возвращает `criteria` и `result` из канонического расчета Results, ограниченного этой связью программы и проекта. Старые поля `experts`/`can_rate` сохранены. В просмотре организатора используются общая матрица и мобильные карточки Results; отдельная кнопка личного оценивания убрана. Средние и итог учитывают только полные валидные оценки, без изменения правил рейтинга.

Сданный проект с `draft=True` остается недоступен для назначения экспертов: в таблице показывается «Черновик заявки», а плашка выбора поясняет необходимость завершить оформление заявки. Это не то же, что публичность проекта (`is_public`). Автоматическая публикация и изменение пользовательских данных не выполняются. Фильтры проектов применяются вместе из модального окна; выгрузка и выбор всех используют примененные фильтры.
