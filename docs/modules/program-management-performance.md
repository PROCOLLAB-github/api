# Нагрузочная проверка управления программой

Для повторного прогона откройте GitHub Actions → **Program management performance**.
Рабочий процесс запускается вручную и при изменении сценария в PR. Каждая
конфигурация поднимает отдельную PostgreSQL 15 и создает синтетические записи
в тестовой базе. Запросы идут по HTTP на адрес Django LiveServer внутри
раннера. Пользователи и данные dev и production в прогоне не используются.

| Профиль | Участники с ответами | Проекты | Эксперты |
| --- | ---: | ---: | ---: |
| `small` | 1 000 | 60 | 12 |
| `large` | 10 000 | 500 | 30 |
| `pressure` | 25 000 | 1 000 | 48 |

Первые два профиля проверяют чтение при одном и восьми параллельных запросах.
Профиль `pressure` дополнительно делает по 72 запроса при параллельности 24
для каждого сценария чтения. Выгрузка Excel выполняется последовательно.

Первый набор охватывает конкурсную программу в режиме проектов. Проверяются
список участников с пагинацией, поиск и фильтры, список проектов, обзор
программы, предварительный расчет распределения, выгрузка Excel и запись
анкеты уже вошедшим пользователем. Регистрация нового аккаунта использует
штатный BCrypt. Подтверждение выполняется по ссылке из письма, перехваченного
почтовым тестовым бэкендом. В контрольной выгрузке проверяются
состав участников, сохраненные ответы и историческая подпись поля.

Артефакт каждого профиля содержит `program-management.json` и
`runner-usage.txt`. JSON фиксирует ревизию, размер данных, число запросов
и параллельных клиентов, p50/p95/p99, пропускную способность, размеры
ответов и ошибки. В `runner-usage.txt` указано потребление ресурсов
всего процесса проверки, включая подготовку данных.

- Сравнивайте одинаковые профили и сценарии. Для сценариев с малым числом
  запросов p95 и p99 могут совпадать с самым медленным запросом. Для новой
  регистрации и подтверждения выполняется по пять параллельных запросов и
  одному прогревочному. Все 12 запросов укладываются в штатный лимит одного IP.
- Функциональные проверки и ошибки используют как критерий прохождения.
  Время на общих раннерах меняется, поэтому единичный замер не служит
  жестким порогом для релиза.
- Результат характеризует указанный объем данных и параллельность. Замер
  пропускной способности сервера с production-конфигурацией и одновременной
  работой всего раздела требует отдельного прогона. В первом наборе не
  измеряются время доставки внешней почты, режим решений, выдача сертификатов
  и время отрисовки фронтенда.
