## Миграции и проверка данных

Новая `users.0066_alter_userachievement_files` привязана к собственным миграциям
master: `users.0065_expand_university_directory` и `files.0007`. Она фиксирует
`through_fields` в состоянии модели; `sqlmigrate` на PostgreSQL дает `(no-op)`.
Также применяются новые миграции beat, passwordreset, taggit и token_blacklist.

Локальная репетиция выполнялась на отдельной синтетической PostgreSQL 16:

1. Исходный master и Django 4.2.11 создали схему, пользователя, программу,
   поданный проект, анкету, достижение с файлом и access/refresh-токены.
2. Кандидат с Django 5.2.18 применил новые миграции. Сравнены хеши строк всех
   таблиц users/projects/partner_programs/files/project_rates: исходные данные
   сохранились, пароль и связь достижения с файлом работают.
3. Старые access/refresh приняты; refresh успешно обновлен. Старый Django 4.2.11
   после миграций также прочитал те же записи и связи.

Это проверка совместимости prod-кода на искусственных данных, не репетиция
на копии рабочей базы. Сетевые обращения к внешним сервисам в ней запрещены.

## Автоматические проверки

В PR CI сохранены отдельный прогон карантина prod API с выключенным NEXTGEN,
проверки блокировок/ограничений PostgreSQL и полный набор с включенным NEXTGEN.
Сборка production Dockerfile выполняется без публикации образа. Внутри образа
проверяются Django, старые пароли, WebP и настоящие PDF: скачивание резюме и
вложение в письмо через локальную тестовую почту.

Обновление не меняет обработчик регистрации с внешнего сайта; его существующие
API-тесты входят в полный набор. Исправление защиты внешней регистрации —
отдельная задача и не считается выполненным обновлением библиотек.

`pip-audit` на 3 ноября 2026 проверил все 141 lock-запись по PyPI: известных
уязвимостей и пропущенных записей нет. Это сведения о Python-пакетах,
не полный аудит приложения или системных библиотек Linux-образа.

Итоговые ссылки CI и точные результаты находятся в описании PR #853.

## До разрешения на выкладку

Ничего из этого PR не сливается и не выкатывается автоматически в рамках
подготовки. Release workflow не запускался; рабочая база не мигрировалась,
контейнеры prod не перезапускались и реальные письма не отправлялись.

Для проверки работающего prod подготовлен отдельный служебный workflow, который
читает состояние контейнеров и выполняет SELECT в транзакции READ ONLY. SSH
подключение требует независимо подтвержденного ключа prod. Проверка сервера
отложена до этапа перед выкладкой; в рамках подготовки PR доступа к prod нет.

Перед выпуском остаются обязательные условия:

- Подтвердить фактические PostgreSQL 14+, исходный коммит/образ prod, состояние
  миграций, свободное место и достаточные права роли мигратора.
- Сверить рабочий коммит с master: в master есть самостоятельные изменения после
  последнего известного release-коммита; их нельзя считать автоматически
  проверенными или уже установленными только по состоянию ветки.
- Создать свежую защищенную резервную копию prod, проверить ее восстановление
  в изолированную базу и применить там миграции кандидата. Сохранить старый образ
  и конфигурацию. Резервная копия dev не является копией prod.
- Выбрать окно выкладки и действия при ошибке. Восстановление всей базы после
  возобновления записи может потерять новые пользовательские изменения; оно
  требует отдельного решения, а не автоматического отката к старому архиву.
- После отдельно разрешенной выкладки проверить действующий фронт, вход/refresh,
  профиль, файлы, программу/проект, внешнюю регистрацию, админку, PDF и очередь.
  Реальную регистрацию или отправку писем согласовывать по конкретным адресатам;
  тесты PR не используют настоящих пользователей.

В текущем release workflow нет автоматического backup. Зеленый CI сам по себе
не снимает перечисленные условия допуска к prod.
