# Обновление зависимостей, 02.11.2026

Изменение подготовлено от backend dev `cf48cd7`. Ветка:
`codex/update-supported-dependencies`. Это отдельное изменение от исправления
внешней регистрации `codex/secure-external-registration`.

## Что меняется

Python остается в серии 3.11. Основная версия Django ограничена веткой 5.2 LTS.
Точные версии и хеши пакетов зафиксированы в `poetry.lock`; обычная установка
не выполняет автоматический переход на Django 6.

| Пакет | Было | Стало |
| --- | --- | --- |
| Django | 4.2.11 | 5.2.18 |
| Django REST Framework | 3.15.1 | 3.18.3 |
| SimpleJWT | 5.3.1 | 5.5.1 |
| Requests | 2.31.0 | 2.34.2 |
| Pillow | 9.5.0 | 13.0.0 |
| WeasyPrint | 62.3 | 70.0 |
| cryptography | 42.0.5 | 50.0.2 |
| bcrypt | 4.1.2 | 4.3.0 |

Также согласованы связанные Django-библиотеки и обновлены транзитивные
зависимости. Вспомогательные Black и setuptools подняты до исправленных версий.
Poetry 2.5.1 используется одинаково в Docker и CI.

## Адаптация приложения

- Настройка `STATICFILES_STORAGE`, удаленная в Django 5.1, заменена на `STORAGES`.
  Сохранены файловое хранилище по умолчанию и сжатие статики WhiteNoise.
- Тестовые настройки админки используют тот же новый формат.
- Явное ограничение `bcrypt<5` сохраняет проверку старых паролей с алгоритмом
  `bcrypt` длиной более 72 байт. Новые пароли продолжают использовать настроенный
  в приложении `BCryptSHA256PasswordHasher`.
- В Docker добавлена системная библиотека HarfBuzz, требуемая новым PDF-движком.
- Загрузчик ресурсов сертификата переведен на `URLFetcherResponse` WeasyPrint 70:
  сохраняются встроенные шрифты и PNG-фоны. Разрешены только собственные шрифты
  и встроенные PNG; сетевые адреса и произвольные файлы по-прежнему отклоняются.
- Установка проекта в CI выполняется с `--no-root`, как и в Docker: это приложение,
  а не устанавливаемая библиотека. Исправлен backend сборки Poetry.

Сущности проектов и решений, режим программы, адреса API и бизнес-правила
регистрации этим изменением не переключаются.

## Миграции и сохранность данных

Новая миграция `users.0066` фиксирует `through_fields` существующей связи файлов
достижения в состоянии Django. Для PostgreSQL `sqlmigrate` показывает `no-op`:
таблицы и записи эта миграция не меняет.

Есть миграции обновленных библиотек: django-celery-beat, django-rest-passwordreset,
taggit и token_blacklist. Их нужно применить штатным мигратором перед запуском
нового образа. Права runtime-роли расширять для этого не нужно.

Проверка перехода выполнена на копии старой тестовой базы PostgreSQL 16:
пользователь с паролем, legacy-программа с проектом и solution-программа с
решением созданы на Django 4.2.11, затем проверены после миграций на Django 5.2.18.
Это проверка совместимости схемы и данных на искусственных записях.
После обновления те же записи успешно прочитаны и старым runtime Django 4.2.11.

Старый фрагмент `Image.ANTIALIAS` в миграции файлов 0007 не исполняется:
`operations` в ней пуст. Историческая миграция не переписана.

## Перед выпуском

1. Убедиться, что PostgreSQL сервера версии 14 или новее, и сделать проверяемую
   резервную копию базы. Версия реального prod-сервера в этой работе не проверялась.
2. Собрать новый Linux-образ из этого lock-файла и прогнать PostgreSQL CI.
3. На dev применить миграции мигратором, затем обновить web и Celery одним образом.
4. Проверить через действующий фронт вход и обновление токена, профиль и файлы,
   старую программу с проектом, новую с решением, сдачу и оценку, админку,
   сертификаты, отправку почты и выполнение фоновой задачи через Redis.
5. После приемки повторить выпуск на prod с сохранением предыдущего образа.

Локальная проверка использует настоящие PostgreSQL и PDF-движок, но почта,
очередь и кеш изолированы тестовой конфигурацией. Она не подтверждает работу
реальных SMTP/CDN/Redis, конфигурацию сервера или поведение открытого браузера.
Локальный Docker не запущен, Linux-образ в этой работе не собирался.

Обновление зависимостей не заменяет исправление внешней регистрации и настройку
ее доверенного отправителя: это самостоятельная найденная проблема.
