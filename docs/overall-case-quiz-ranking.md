# Общий рейтинг кейс-чемпионата

## Требование и текущий контур

Организатору нужен один итог команды: оценка кейса от 0 до 100 плюс результат
квиза от 0 до 100. Максимум — 200. Пользователь 12 ноября подтвердил простое
сложение и доступ только организатору. Отдельных долей этапов 70/30 нет.
Проценты критериев остаются внутренней частью оценки кейса.

База реализации — ветка пилота API, runtime до изменений `7657082`.
`partner_programs/services/results.py:results_data` уже считает экспертные
оценки и готовность сданного Project; `project_rates/evaluation_math.py`
содержит общий расчет и места 1, 1, 3. Проект связан с программой через
`PartnerProgramProject`, уникальный по программе и проекту. Это существующая
команда чемпионата; Application/Team/Submission и ProgramSolution сюда не входят.
Квиз с командной попыткой пока не реализован и остается отдельной задачей
после согласования дизайна. Курсовые ответы не являются результатом этого квиза.

## Расчет и состояния

- `итог = кейс + квиз`, без изменения масштаба и без дополнительных коэффициентов.
- Кейс использует готовый `weighted_percent`: официальные баллы из существующего
  расчета, округленные до сотых. Нужны сданный проект и требуемое число полных
  экспертных оценок. Предварительный балл кейса можно видеть отдельно.
- Legacy-режим не превращается автоматически в шкалу 0–100. До настройки весов
  новый рейтинг явно сообщает, что расчет кейса не настроен; прежний рейтинг
  кейсов продолжает работать по старому контракту.
- Квиз передает окончательный нормализованный балл 0–100 с точностью до сотых.
  Правильность, частичные ответы, скорость и нормализация относятся к модулю
  квиза. Общий рейтинг не пересчитывает ответы и время.
- Пока любой этап не завершен, итог и место — `null`. Отсутствующий балл
  не заменяется нулем; настоящий ноль является завершенным результатом.
- Все команды программы видны одной таблицей, включая еще не сдавших кейс.
  Общие места считаются по всем готовым командам программы, до поиска/фильтров;
  равные итоги делят место: 1, 1, 3. Имена/ID задают только стабильный порядок строк.
- Состав команды и правила сдачи/приглашений сохраняются. Результат относится
  к паре программа × проект, а не к лидеру или отдельному участнику.

## Результат квиза и границы записи

Новая добавочная `ProgramQuizOutcome` хранит программу, проект, уникальный
серверный идентификатор попытки, балл и время получения результата. Пара
программа × проект уникальна. Результат сохраняется при удалении и повторном
создании связи участия: это не дает вторую попытку того же проекта. Удаление
самого проекта/программы использует обычный cascade.

Внутренний сервис `record_quiz_outcome` вызывается будущим серверным модулем
квиза после завершения попытки. Он проверяет текущую связь с программой,
использует существующий порядок блокировок `lock_team`, принимает только
конечные баллы 0–100 и глобальный непрозрачный идентификатор попытки. Повтор
того же результата идемпотентен; другая попытка/другой балл конфликтуют.
Одна попытка не может использоваться для другой команды.

Публичного POST/PUT для загрузки баллов нет. Участник, эксперт и организатор
не задают балл квиза вручную. В Django admin результат доступен только для
чтения. Исправление/пересчет завершенной попытки требует отдельного явного
контракта и в эту задачу не входит.

## API и права

Новые organizer endpoints:

- `GET /programs/{id}/management/overall-results/` — общий расчет и строки.
- `GET /programs/{id}/management/overall-results/export/` — тот же расчет в XLSX.

Права берутся из существующего `managed_program`: manager своей программы либо
staff. Гость/участник/эксперт/чужой manager не получают данные. Ответы private,
no-store. Django admin дополнительно проверяет модельные права программы.
Новые действия чтения/экспорта доступны и через карточку программы в admin,
с общей бизнес-логикой. Остальные endpoints/поля не меняются.

Фильтры совместимы по смыслу с `ResultsQuery`: поиск, кейс, complete/pending,
порядок, scope экспорта current/all. Невалидный фильтр — 400; неизвестная
программа — 404; недостаточные права — 403; неподдерживаемый контур решения
или неконкурсная программа — 409. Нельзя смешать Project и ProgramSolution.

Ответ содержит программу, дату расчета, максимумы 100/100/200, признак настройки
кейса, число готовых команд и `projects`. Строка содержит ID связи и проекта,
название команды, кейс, баллы/готовность каждого этапа, счетчик экспертов,
общий итог, место и явный статус ожидания. Персональные оценки/почты экспертов
и идентификатор попытки в этот ответ не включаются.

## Интерфейс и выгрузка

Существующий экран результатов кейса сохраняется. Для Angular готовится
дополнение существующего раздела оценивания: общий рейтинг с колонками места,
команды, кейса, кейса из 100, квиза из 100, итога из 200 и состояния. Нужны
loading/empty/error/no results, ожидание этапов и корректный настоящий ноль.
Новый Angular UI требует отдельного конкретного дизайн-превью и подтверждения;
до этого независимы серверный расчет, API, admin и XLSX. Экран квиза не меняется.

XLSX использует единый серверный snapshot: итоговая формула только для готовых
строк, неподготовленные итоги/места пустые. Названия записываются как текст,
чтобы исключить исполнение формул из пользовательских строк. Arial 10,
белый фон, жирная только первая строка, закреплена только шапка, без закрепления
столбцов и служебных листов.

## Acceptance criteria и план проверки

- O01: готовые этапы 80 и 90 дают 170 из 200; 100+100 дают 200; 0+0 дают 0
  и участвуют в рейтинге. Проверки математики/API/XLSX.
- O02: нет квиза, не сдан кейс или не хватает полной экспертной оценки —
  итог/место пусты, отдельные готовые баллы сохранены. Legacy не нормализуется
  скрыто. Проверки API с реальными данными и регрессия обычных результатов.
- O03: проект в двух программах не смешивает результаты; повторное участие
  того же проекта сохраняет единственную попытку. Проверки сервиса и БД.
- O04: повтор записи той же попытки/балла не меняет запись; конфликтующий
  повтор и повтор чужой попытки отклоняются. Диапазон/NaN/Infinity/лишняя точность
  отклоняются; уникальность и диапазон проверяются PostgreSQL.
- O05: manager своей программы/staff читают; остальные роли, гость и чужой
  manager не получают API/export/admin. Прямые HTTP/negative tests.
- O06: равные итоги делят место, поиск/фильтр не меняют глобальные места;
  ожидающие команды не получают место. Tests на нескольких кейсах/командах.
- O07: XLSX повторяет баллы/места/статусы API, считает простую сумму готовых
  этапов и сохраняет настоящий ноль. Проверки книги/формул/инъекций/оформления.
- O08: Django admin и API используют один расчет; admin не разрешает ручное
  изменение результата квиза. Tests прав, GET/POST и отображения.
- O09: добавляется только новая таблица. Миграция не меняет существующие
  программы/оценки/участников; прежние API/расчет/веса проходят регрессию.
- O10: число запросов не растет на один запрос для каждой команды; конкурентная
  запись одной попытки не дает дубликат. Query-count и PostgreSQL transaction tests.
- O11 (Angular): после подтверждения конкретного экрана организатор видит новый
  общий рейтинг по серверному контракту; loading/empty/no results/error/pending/
  zero, mobile, keyboard и прямой переход проверены в браузере. До подтверждения
  это отдельный ожидающий этап, а не готовый runtime UI.

Порядок реализации: schema/model и внутренняя запись результата → общий
read-service → API/export/admin → PostgreSQL/migration/regression → review/PR.
Angular дизайн готовится по существующим результатам и PROCOLLAB controls;
реализация нового UI идет после его подтверждения. До готового квиза реальные
строки будут ожидать его результат; тестовые баллы проверяются только на
изолированной БД, в живой пилот не записываются. Dev/prod не обновляются.

## Порядок будущего обновления

Совместимый backend → одна добавочная 0045 → согласованный Angular экран.
Исторический `upgrade_weights.py` разрешает только две миграции весов и не
является установщиком общего рейтинга. Для живого пилота нужен отдельный
проверенный пакет поверх актуального source/UI и безопасный rollback.
Его установка в этом изменении не выполнялась. Не следует подменять старые
fingerprints/whitelist вручную или запускать повторно установщик весов.

При откате приложения новую таблицу сохраняют; автоматического удаления
результатов или восстановления всей БД поверх текущих данных нет. Существующие
регистрация, приглашения, критерии, оценки и данные команды не пересоздаются.
